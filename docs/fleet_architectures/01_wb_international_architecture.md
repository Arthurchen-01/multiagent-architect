## 二、 深度病理解剖：为什么过去“来回反复改、Bug 层出不穷”？

复盘近期的工程历史，系统陷入死循环的根本原因并非单个函数的语法 Bug，而是**六大系统级架构盲区导致的“拆东墙补西墙”**：

### 1. 致命病根：号在排队里烂掉（91% 撞手机墙判死）与鲜度维度缺失
* **历史现场**：34 个死号里有 31 个死于“手机墙（Google 强制要求绑手机号）”。过去排查人员误以为是“出口 IP 脏了”或“打码模型挂了”，疯狂更换代理、修改打码，结果依然大面积死号！
* **铁证真相**：进货渠道 `yx-mail` 明确标明商品是**30 分钟临时验证码服务，不保活**。而实际流程是 10-04 采购的号，在队列里堆积到 10-05 甚至 10-06 才跑（拖延 24~48 小时），账号自然过期被风控拦截。
* **架构缺陷**：任务台账只记“是什么、跑没跑”，**完全没有记录“什么时候买的（鲜度 `bought_at`）”**。

### 2. 致命病根：跨节点严重代码漂移（Code Drift）
* **历史现场**：在 1030A/B 上修复了人机 chooser、2FA 处理、Xvfb 加固等 537 行代码后，量芯云-1011 依然疯狂报错。
* **铁证真相**：量芯云-1011 容器里一直跑着 4 天前的旧引擎（10-02 版本），根本没有同步更新。“本地以为修了，远端其实没动”，导致排查人员误以为修复方案无效而反复回退代码。

### 3. 致命病根：Git 浅克隆陷阱与账本文件污染
* **历史现场**：本地仓库为深度 78 的浅克隆，`git status` 伪报 ahead 78 / behind 1；工作树里挂着 342 条删除与新增变动。
* **铁证真相**：`ghsync.py:614` 直接调用 `git add -A`，一旦入库一个新号，会无差别把未验证的工作区代码连同账号台账一起推上 GitHub，极易污染远程主分支。

### 4. 致命病根：网关全局并发锁死导致雪崩（Concurrency Starvation）
* **历史现场**：拥有 256 个有效账号，但下游批量任务 `dsh` 频繁超时卡死，p50 延迟高达数秒。
* **铁证真相**：网关配置中 `max_in_flight_global=2`，全局并发被死死限制为 2。256 个号被饿死，客户端被迫排队，排队超时又引发客户端不断重试，造成惊群雪崩（Thundering Herd）。

### 5. 致命病根：服务器重启后的“自启幽灵进程”（Ghost Daemons）
* **历史现场**：服务器一旦重启，系统负载瞬间飙高，内存爆满。
* **铁证真相**：许多已废弃或下线的爬虫/Worker（如 `cc-modeling-01`, `samurai-crawl-hj`）被注册在 `systemd` 开机自启中。`systemctl stop` 只是临时停止，重启后自动复活并空转，抢占网卡和 CPU。

### 6. 致命病根：反向代理依赖本机 Windows（Single Point of Failure）
* **历史现场**：日本出国链路动辄中断，Antigravity 和 Claude 容器服务全盘挂掉。
* **铁证真相**：远端节点的代理依赖本地 Windows 机器上的 `verge-mihomo.exe` 通过 SSH 反向隧道（17890 ➔ 17891）穿透。只要本地电脑休眠、断网或代理重启，云端生产服务秒级暴毙。

## 三、 工业级防 Bug 架构规范（硬编码不变量）

为了彻底焊死上述漏洞，必须建立以下刚性治理约束：

```
┌────────────────────────────────────────────────────────────────────────┐
│                   🛡️ wb-international 刚性防御守卫                     │
├────────────────────────────────────────────────────────────────────────┤
│ 1. 鲜度守卫 (Freshness Invariant)                                      │
│    - 下单写入 bought_at 毫秒级时间戳                                    │
│    - fresh_minutes = 60 (排队超过 60 分钟强制标记 EXPIRED，绝不入跑号队列) │
│    - 进货背压联动: 仅当「待跑队列 < 空闲 Worker 数」时允许触发采购       │
├────────────────────────────────────────────────────────────────────────┤
│ 2. 代码对齐守卫 (FleetSync Invariant)                                  │
│    - 禁止通过 SSH 直接在单台服务器上手动修改代码                        │
│    - 任何变更上线，必须运行 FleetSync 对齐三台 server.py SHA-256 哈希   │
│    - 若 SHA-256 不一致，网关自动将该节点置为 DRAIN (排空下线)            │
├────────────────────────────────────────────────────────────────────────┤
│ 3. 隔离提交守卫 (Git Decoupling Invariant)                             │
│    - 彻底废除 git add -A                                               │
│    - 账本入库只允许针对 store/accounts.json 执行单文件受控 Commit       │
│    - 本地代码仓禁止浅克隆 (git fetch --unshallow)                      │
├────────────────────────────────────────────────────────────────────────┤
│ 4. 并发与熔断参数基准 (Gateway Concurrency Standard)                  │
│    - max_in_flight (单号并发) = 2                                      │
│    - max_in_flight_global = min(活跃账号数 * 2, 200)                   │
│    - 轮询策略: 严格执行 Response Time Weighted (慢号自动降权)          │
└────────────────────────────────────────────────────────────────────────┘
```

## 四、 节点配置与排障命令矩阵 (Runbook)

### 1. 每日跨机健康核验（一键命令）
```bash
# 在 D:\服务器管理 下执行：
python _ops\fleet_health.py 五四云-1030A 五四云-1030B 量芯云-1011 五四云-1023
```

### 2. 跨机代码 SHA-256 对齐抽检
```bash
# 核验三台引擎代码是否绝对一致
python -c "
import subprocess
nodes = ['156.225.28.208', '156.225.28.4', '154.94.225.214']
for ip in nodes:
    cmd = f'ssh root@{ip} docker exec wbfarm sha256sum /app/server.py'
    print(ip, subprocess.getoutput(cmd))
"
# 验收标准：三台输出的 SHA-256 哈希必须 100% 相同！
```

### 3. 网关 7864 并发与延迟监控
```bash
# 登录五四云-1023，查看当前排队与首字延迟
journalctl -u workbuddy2api-n11 --since '1 hour ago' | grep -oE 'TTFB=[0-9]+ms' | sort -n
# 验收标准：p50 首字延迟必须 <= 1200ms
```

### 4. 幽灵自启清理确认
```bash
# 确认没有任何处于 enabled 状态的无主单元
systemctl list-unit-files | grep -E 'cc-|samurai-' | grep enabled
# 验收标准：输出必须为空！
```
