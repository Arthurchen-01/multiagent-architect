## 一、 系统定位与核心痛点

### 1.1 业务背景
日本乐天市场（`rakuten.co.jp`）与知乎（`zhihu.com`）是典型的高防电商与社交媒体平台。乐天采用双层风控架构（外层 Akamai Bot Manager + 内层自研确定性设备指纹 `device_fp` 及 JWE 加密串）；知乎则采用高频反爬挑战（动态签名、Cookie 刷新限制及评论分页熔断）。本架构旨在实现**多机集群分布式分片高吞吐采集**与**高可用证据归档**。

### 1.2 历史多服务器协作 4 大死穴与根因分析
1. **乐天 Akamai 判据与 `_abck` 认知误区**：
   - *病根*：旧代码盲目将“必须获取到有效 `_abck`”作为可用判据。实测发现：乐天在未被挑战时仅下发 `ak_bmsc`，裸请求与正常浏览器根本不给 `_abck`。原判据直接将 100% 正常会话当场判定为不可用；
   - *整改*：重构 `SessionHealth.usable` 判定逻辑：`missing`（未挑战）与 `validated`（验证通过）均视为可用放行，仅在出现 `not_validated`（下发传感器但未被接受）时阻断。
2. **同账号设备指纹漂移触发乐天风控**：
   - *病根*：多次登录同账号时随机生成环境参数，导致乐天自研 `device_fp` 频繁变更，系统直接将其判定为“异地盗号”并实施封号；
   - *整改*：通过 `read_client_signals` 从账号唯一标识确定性派生 `device_fp`、时区强制锁定为 JST `-540`、系统平台锁定为 `Win32`，确保同账号多机调度时指纹 100% 恒定。
3. **分片混乱与 7 个孤儿进程在 1021 机器上“暗中空转”**：
   - *病根*：早期分片缺乏统一部署清单，五四云-1021 上常驻了 7 个采集进程，但主控文档中从未记载；
   - *整改*：统一划分 `s1`~`s7` 分片标准，并将控制台集中收敛至五四云-621（`:8791`），通过 Token 进行鉴权管控。
4. **知乎采集反爬风控导致 IP 频控封锁**：
   - *病根*：单机高频爬取专栏触发 403 频控，返回空响应；
   - *整改*：五四云-1023 服务采用 Playwright Stealth 无头浏览器，注入动态 Cookie 池并保持人类阅读节奏（Random Jitter），并将结构化文章落盘为 Markdown / HTML 实体。

## 四、 防风控与死锁故障自愈规范 (Anti-Bug Runbook)

### 4.1 故障场景 A：乐天触发 Akamai 拦截 (`not_validated`)
- **触发表现**：请求返回 403，页面下发 `/akam/13/b465e6` 传感器脚本且 `_abck` 变为未通过状态。
- **自愈机制**：
  1. 立即暂停该分片后续任务，记录触发会话的 IP 与环境；
  2. 启动 Playwright 无头浏览器模拟真实用户鼠标平滑移动（Bézier Curve）与视口滚动，重新生成有效的传感器载荷；
  3. 若重试 2 次仍无法通过，调用代理池 API 切换当前节点出口 IP，并丢弃当前污损的 Cookie 会话。

### 4.2 故障场景 B：分片执行孤儿化或进度冲突
- **触发表现**：两台机器同时修改同一分片文件（例如 `runs/060/shards/s4.json`），导致数据覆盖丢失。
- **排查与规避**：
  1. 严格落实**机器物理与分片号唯一绑定**：621 专职负责 `s4`，620 专职负责 `s5`，1021 专职负责 `s1`~`s3`；
  2. 每个分片文件头部携带 `worker_id`、`lease_expires_at` 与 `machine_hash`；
  3. 写入前使用带毫秒戳的临时文件原子重命名（Atomic Rename），彻底杜绝并发写冲突。

### 4.3 故障场景 C：知乎反爬返回验证码拦截页
- **触发表现**：响应状态码 200 但 HTML 包含 `安全验证` 或 `captcha`，真实正文为空。
- **排查与自愈**：
  1. 爬虫解析器匹配到验证码关键字后，立即触发 `PROOF_FAILED` 并截取当前页面现场；
  2. 将该目标放入延迟重试队列（指数退避 15 分钟）；
  3. 切换至带有已登录 Session Cookie 的可用长效账号继续拉取。
