## 一、 系统定位与核心痛点

### 1.1 业务背景
在个人开发者驱动大规模云服务器机队的场景下，单靠人力或者单个单一 Agent 极易陷入“盲猜改代码”、“修改引起次生灾害”、“远程执行无凭证虚假完成”的恶性循环。本架构集群提供了**标准化的三智能体协作开发模板（Three-Agent Runtime）**、**量化决策分析工具**、**游戏化激励系统**与**跨设备（Chromebook / PC / 云服务器）无缝编码基础设施**。

### 1.2 历史多服务器协作 4 大死穴与根因分析
1. **单一 Agent 既当裁判又当运动员（Lack of Review Segregation）**：
   - *病根*：一个 Agent 自己写代码、自己跑测试、自己宣布“已修复”，导致假修复和回退严重；
   - *整改*：`three-agent-runtime-template` 严格推行“大伟程序员”提倡的 **SDD (Spec-Driven Development)** 架构：
     - **智能体 1 (Engineer)**：负责根据规约原子编写代码；
     - **智能体 2 (Reviewer)**：独立运行自动化测试并提取真实环境证据（CF-RAY/现场截屏）；
     - **智能体 3 (Arbiter)**：拥有绝对裁决权，基于物理证据链核准后方可归档合并。
2. **量化金融指标计算的数据漂移与断点丢失**：
   - *病根*：单机抓取股票行情因 IP 封禁或进程退出导致 K 线指标计算断裂；
   - *整改*：`stock-shanzhang` 实现分时与日线多级持久化缓存，通过分布式心跳对齐行情时间戳。
3. **长期高强度开发的心理疲惫与执行无反馈**：
   - *病根*：多机任务后台静默运行，开发者缺乏即时正面反馈；
   - *整改*：`Heart-Beat-War` 与 `achievements` 引入成就系统与作战室仪表盘，将代码提交、任务完成、Bug 消除转化为可量化的经验值与成就勋章。
4. **移动/跨设备编码环境配置繁琐**：
   - *病根*：外出使用 Chromebook 或备用笔记本时无法访问本地开发环境和私有云机队；
   - *整改*：`could-coding` 与 `chromebook-dragonfly-drive` 搭建标准容器化 Web IDE（code-server / OpenHands），通过安全 SSH 反向隧道直通云端机队。

## 二、 核心架构设计与协作工作流

### 2.1 三智能体仲裁与状态机闭环 (Tri-Agent Arbiter Lifecycle)

```
                       ┌───────────────────────────────┐
                       │   用户需求 / GitHub Issue     │
                       └───────────────┬───────────────┘
                                       │ 转换为机读规约 (.spec)
                                       ▼
                       ┌───────────────────────────────┐
                       │     待办队列 tasks/pending/   │
                       └───────────────┬───────────────┘
                                       │
        ┌──────────────────────────────┴──────────────────────────────┐
        ▼ (1) 原子加锁认领                                            ▼ (2) 编写代码与单测
┌──────────────────────────────┐                              ┌──────────────────────────────┐
│       Engineer Agent         │ ───────────────────────────► │  产出 Diff 与单元测试脚本    │
│  (原子实现，禁止盲猜修改)    │                              └──────────────┬───────────────┘
└──────────────────────────────┘                                             │
                                                                             ▼ (3) 物理证据收集
                                                              ┌──────────────────────────────┐
                                                              │       Reviewer Agent         │
                                                              │ (真核验证: 截屏/网络报文/日志)│
                                                              └──────────────┬───────────────┘
                                                                             │
                                       ┌─────────────────────────────────────┘
                                       ▼ (4) 提交证据包与审查报告
                       ┌───────────────────────────────┐
                       │        Arbiter Agent          │
                       │    (终审仲裁: 校验 4 大铁律)  │
                       └───────────────┬───────────────┘
                                       │
                  ┌────────────────────┴────────────────────┐
                  ▼ [证据不足 / 存在回归]                   ▼ [证据链确凿闭环]
      ┌──────────────────────────────┐          ┌──────────────────────────────┐
      │  退回重构 (REJECTED)         │          │  批准归档 (COMPLETED)        │

      └──────────────────────────────┘          └──────────────────────────────┘
```

## 四、 防死锁与断网自愈策略 (Anti-Bug Runbook)

### 4.1 故障场景 A：Reviewer 与 Engineer 意见不一致，任务陷入僵局
- **触发表现**：任务在 Reviewer 处多次被打回，循环超过 3 轮。
- **自愈机制**：
  1. 触发 `ArbiterEngine` 强制仲裁介入；
  2. 仲裁员自动提取双方测试日志与 Diff 片段，进行硬指标对齐（单元测试通过率是否 100%、是否有未捕捉异常）；
  3. 若判定代码无语法与逻辑漏洞，仲裁员直接签署豁免令并推进至完成；若判定存在硬伤，冻结当前任务并由主控开发者人工复核。

### 4.2 故障场景 B：移动端 / Chromebook 网络中断导致开发中断
- **触发表现**：SSH 会话断开，正在执行的编译或长耗时测试被 SIGHUP 杀死。
- **排查与规避**：
  1. 所有云端任务强制使用 `tmux` 或 `systemd-run` 后台化守护；
  2. `could-coding` 环境统一接入持久化 Session 机制；
  3. 客户端重新连接后，直接通过 `tmux attach` 恢复上一刻完全相同的工作现场。
