# 项目记忆（状态放哪、怎么写、多个人怎么不打架）

> 什么时候读：接手一个不熟的仓库、要把状态交给别人、或者准备往项目里写结论时。
>
> **核心事实**：**skill 记不住项目状态。** 通用规则、诊断方法、流程写在本 skill 里；
> 项目特定的事实（数据、决策、任务状态、测试结果）**只能写在项目自己的文件里**。
> 谁要是凭「上次会话里说的」讲项目现状，直接当错处理。

---

## 一、开工先读什么（顺序固定）

| 顺序 | 读什么 | 回答什么问题 |
| :-- | :-- | :-- |
| 1 | `AGENTS.md`（或等价的工作区说明） | 这个工作区的边界、红线、口径 |
| 2 | `README` / 导航文件 | 这个项目是什么、从哪进 |
| 3 | 进度账本 / 总进度表 | **现在到哪一步** |
| 4 | 决策记录 | 为什么是现在这个做法（避免把已否决的方案再提一遍） |
| 5 | 经验教训 / 问题记录 | 踩过什么坑，**动手前必扫** |
| 6 | 待办 | 谁在等什么 |
| 7 | 最近一次验收报告 | 上次交付时证据是什么 |

**读不完就先读 3 和 5** —— 这两份最能防止你把已经决定过的事重新讨论一遍、把踩过的坑再踩一遍。

> 每个单元该有哪些文件、各自什么格式，由 `project-skeleton-architecture` 这个 skill 定义。
> **本文件不抄它的内容** —— 需要时去读它，避免两份规矩打架。

---

## 二、往项目里写什么（三条硬规矩）

1. **快照与账本分开。**
   「快照」是某一天的定稿（不可再改）；「账本」是持续追加的记录。
   两者混在一个文件里，就没法判断哪句是当时的结论、哪句是后来的补充。

2. **决策记录只追加，永不修改，只取代。**
   改了主意不要改旧条目 —— 新开一条，写明「取代第 N 条」。
   否则后人看到的是一份「一直都对」的历史，学不到任何东西。

3. **经验教训每条必须带「防复发行动项 + 谁负责」。**
   没有行动项的教训 = 感想，下次照犯。

## 三、落盘检查（交之前）

- [ ] 结论写进文件了吗？（**只留在对话里 = 不存在**）
- [ ] 登记进项目索引了吗？（没登记 = 后人找不到 = 等于没写）
- [ ] 文件名能让人猜出内容吗？（日期 + 主题，别叫 `新建文档.md`）
- [ ] 状态词用的是 ✅ / ⬅️ / ⏳ 吗？（**不许**「部分完成」「基本可行」）

---

## 四、多个人/多个 Agent 同时写，怎么不打架

| 冲突 | 做法 |
| :-- | :-- |
| 同时改同一个文件 | **一人一文件**，最后合并；不要两个人往同一张表里插行 |
| 谁负责哪件事 | 每条任务**必须带归属**（谁做、谁验收），没有归属的任务等于没人做 |
| 追加型记录（日志/决策） | 用**追加**而不是改写；追加冲突最容易人工解决 |
| 状态字段 | 只有一个地方能改（唯一真相源），其他文件**引用**它，不复制它 |
| 并发验收 | 验收人 ≠ 实现人。**自己说自己好不算验收。** |

## 五、交接（把状态交给别人 / 接别人的活）

分清两种卡：

- **线卡**：随**一条线**走，原地更新，长期有效（「这条线现在什么状态、文件在哪、踩过什么坑」）。
- **交接卡**：随**一次活**走，一次性（「这次做到哪、下一步是什么、缺什么输入」）。

交接卡必须能独立看懂，**不许写「见上文」**。读者回答不出下面四问，就是没写清楚：

1. 目标是什么？
2. 现在在哪？
3. 下一步干什么？
4. 为什么现在能干了（输入齐了吗）？

---

## 六、待办（防止「说过就等于做了」）

- 听到新任务 → **立刻写进待办文件**，不要只在对话里答应一句。
- 做完 → 把那一行勾掉。
- 待办文件是**唯一真相源**；别的文件、聊天记录都不算。
- 每天给用户的第一句话，是**「你现在要做的一件事」**，而且**只能一件**。

---

## 七、给用户看的汇报（状态怎么呈现）

状态只有三种：**✅ 完成 / ⬅️ 现在在这 / ⏳ 没开始**。
流程必须有图（ASCII 生产线或表格），**每道工序必须标产出文件**；
「下一步」**只能写一件事**，并逐项标出它的输入是否就位。

> 本项目（这台机器上）的汇报格式以项目库里的《工程图式汇报》文件为准；
> 换到别的项目时，用 `assets/report-template.md` 里的七段骨架。
