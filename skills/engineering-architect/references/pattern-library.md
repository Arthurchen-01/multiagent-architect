# 模式库（Pattern Library）

> 什么时候读：要设计、要判断「这是哪一类问题」、要复核别人的方案时。
>
> **用法**：从上往下扫一遍，找**识别信号**里你正看到的那一条。找到就照「解决原则」走，
> 并**先做「验证实验」**再动手改 —— 模式是假设，不是判决。

---

## 一、八类基础模式（诊断视角，不是流程）

这八类不是每个项目都要逐项展开的清单，而是**八个看问题的角度**。
一个问题通常同时命中两三类，**按代价最高的那一类先处理**。

| 类 | 看什么 | 典型识别信号 | 初学者最常见的误判 |
| :-- | :-- | :-- | :-- |
| **分解** | 责任、模块、边界、接口 | 一个文件/函数什么都干；改 A 必须改 B；没人说得清谁负责 | 「先写出来再拆」→ 拆不动了 |
| **状态** | 任务状态、状态机、持久化、事件 | 重启后状态丢失；同一件事被做两遍；不知道现在到哪一步 | 「Agent 太笨」→ 实际是没持久状态 |
| **约束** | Schema、权限、规则、不变量 | 脏数据进库；越权访问；同一个字段三种写法 | 「加个判断就行」→ 判断散落在十处 |
| **不确定性** | 证据、来源、适用性、置信度 | 报告里的数字查不到出处；模型很自信但没依据 | 「看着合理」当证据 |
| **反馈** | 测试、评估器、人工验收 | 改完不知道好没好；回归；「应该没问题」 | 「测过了」= 手动点过一次 |
| **资源** | 性能、并发、缓存、队列、调度 | 慢；偶发超时；一并发就乱 | 「协议没油水了」→ 其实没量过握手成本 |
| **故障** | 超时、重试、幂等、回滚、隔离 | 重试造成重复扣款/重复写；失败后留下半成品 | 「加重试」→ 变成重复提交 |
| **演化** | 抽象、版本、兼容性、渐进架构 | 新旧两套并存；改一处崩三处；不敢升级 | 「一次重构到位」→ 长期停在分支上 |

## 二、已经踩出来的模式（每条都有真实案例）

每条格式固定：**识别信号 → 底层机制 → 常见误判 → 解决原则 → 适用边界 → 验证实验 → 案例**。

### P-01 用模型智能弥补系统缺陷 ｜类：状态 · 反馈

- **识别信号**：Agent 重复做同一件事、漏做、做完自己不知道做完了；换个提示词好一阵又坏。
- **底层机制**：缺的是**系统能力**（任务 ID、持久状态、幂等、明确验收），不是模型能力。
- **常见误判**：「模型太弱」→ 于是不停改提示词，问题周期性复发。
- **解决原则**：保持模型不变，先补状态与验收；把「做完了」变成机器能查的条件。
- **适用边界**：模型本身确实不具备该能力时（如看不懂图片）不适用，那是能力缺口不是系统缺口。
- **验证实验**：**只改状态与验收、不改提示词**，跑同一批任务，看复发率是否下降。降了 → 系统缺陷成立。
- **案例**：多步任务反复重跑，改成「任务 ID + 落盘状态 + 幂等写入」后不再重复。

### P-02 截断指纹 ｜类：约束 · 不确定性

- **识别信号**：一批产物的某个维度取值**高度雷同**，直方图上某个值出现异常尖峰。
- **底层机制**：上游有硬编码上限（切片 `[:40]`、参数 `limit=30`），产物被**静默**截断。
- **常见误判**：「数据源本来就这么少」→ 去下游找原因，白跑一天。
- **解决原则**：先怀疑上游有上限；拿「恰好相等」这个尖峰反查代码里的常量。
- **适用边界**：只对**恰好相等**的尖峰成立。自然分布也会在整数附近聚集，要先排除。
- **验证实验**：取被截掉之后的内容（第 41 条起），看它的来源是否与被保留的同类 ——
  同类却被砍掉，截断成立。
- **案例**：学校材料清单库，248 个文件里 **225 个恰好 30 条**。查下去发现**两道**上限
  （抽取层 40 条 + 写文件层 30 条），本科项被挤出库，而下游还按「全都在」在用。

### P-03 双真相源 ｜类：分解 · 演化

- **识别信号**：同一个问题有两个答案、两个文件、两个服务；没人知道该读哪个；统计口径对不上。
- **底层机制**：新旧两套并存，没有一方被作废。下游各自挑一个，于是「都对但不一样」。
- **常见误判**：「先都留着，慢慢迁」→ 两套都长，迁移永远不开始。
- **解决原则**：**归档旧的那套**（移进 archive 并写一句为什么），留下唯一一个。
  只标记「已废弃」不算，因为下游还会读到它。
- **适用边界**：真的需要并行（如灰度期）时，必须指定**谁是唯一真相源**，另一套只读且带过期时间。
- **验证实验**：随机抽 5 个下游消费者，问它读哪一套。答案不唯一 → 双真相源成立。
- **案例**：同一批数据存在「产品层人工核过的一份」和「爬虫层自动产的一份」，
  后者**没有下游消费者**却一直被当成依据统计，把结论虚高了一倍。

### P-04 契约错位（少一层 / 名字对不上） ｜类：分解 · 反馈

- **识别信号**：**点了没反应、没提示、没报错**；控制台只有一条 404；功能「静默失效」。
- **底层机制**：调用方与被调方的路径/字段/层级不一致（例：前端调 `/a/<id>/sessions`，
  后端只有 `/a/:threadId`），**少一层**就匹配不上。
- **常见误判**：以为是网络问题或前端 bug → 在错的一侧查半天。
- **解决原则**：把**两端并列打印**再比对；缺的接口要么补、要么前端明说「还在开发中」——
  死按钮比没有按钮更伤信任。
- **适用边界**：只在「无报错的失败」上优先怀疑；有明确报错时先看报错。
- **验证实验**：写一个「端点存在性」检查（遍历前端调用的每个路径，逐个探后端）。
  红的就是错位点。
- **案例**：选校页一个按钮实测无弹层、无提示、无报错，根因是前端多了一层路径。

### P-05 占位数据泄漏到生产 ｜类：约束 · 不确定性

- **识别信号**：数字看起来**合理但查不到来源**；由随机/哈希生成；和常识差一个量级。
- **底层机制**：种子脚本或占位数据被当成真数据发布；前端对空值不隐藏，于是「有值就是真的」。
- **常见误判**：「先有数再说」→ 用户照它做决策，信任一次性烧掉。
- **解决原则**：**宁可空着**。数据为空时前端整块隐藏；宁可少显示，不显示假的。
- **适用边界**：演示环境可以有假数据，但必须在界面上标明「示例数据」。
- **验证实验**：把每个对外数字反向追一遍来源；追不到的列成清单，一次性清空。
- **案例**：学校详情页的规模/录取率曾是哈希随机生成的（某校显示 2.7 万人、真实约 2.4 千），
  改为写空 + 前端隐藏。

### P-06 构建期常量泄漏 ｜类：故障 · 演化

- **识别信号**：线上包/镜像/产物里出现 `localhost`、内网地址、开发端口、测试密钥。
- **底层机制**：地址写死在源码里，构建时原样打进产物；源码里看着正常，产物里才露出来。
- **常见误判**：「源码里改过了」→ 但**产物没重打**，或者另一处还写着。
- **解决原则**：**验收扫产物，不扫源码**。把「产物里不许出现 localhost」写成一条自动检查。
- **适用边界**：本地开发包不受此限；判断依据是「这份产物会被真实用户加载吗」。
- **验证实验**：对**线上正在跑的那份产物**做字符串扫描（localhost / 127.0.0.1 / 内网段 / 端口）。
- **案例**：线上包里写死 `localhost:4000` 等 5 处，真实访客的浏览器在找他**自己电脑**上的端口。

### P-07 先量再优化 ｜类：资源

- **识别信号**：准备做性能优化，但**没有基线数字**；凭感觉认为「瓶颈在 A」。
- **底层机制**：直觉定位的瓶颈，通常是**你最近看过的那段代码**，不是真正的瓶颈。
- **常见误判**：「协议层面没油水了」→ 于是放弃，其实真正的大头在连接建立/序列化/IO。
- **解决原则**：先量三件事：**总耗时、被调用次数、单次成本**。再动刀。
- **适用边界**：总耗时已经满足需求时不必优化（优化本身有引入 bug 的成本）。
- **验证实验**：同一作业跑两次，一次复用连接、一次每次新建，比总耗时。
- **案例**：每次新建连接 5835ms vs 复用同一条 317ms（**约 18 倍**）；
  作业级实测平均提速 **14 倍**，且判定结果无变化。

### P-08 测量口径与被测对象不一致 ｜类：反馈

- **识别信号**：测试通过了但线上仍然坏；两个测试对同一件事结论相反；结果时好时坏。
- **底层机制**：测试**采样方式**和生产**运行方式**不同（例：生产跑 3 次投票取多数，测试只跑 1 次）。
- **常见误判**：「测试是绿的」→ 把不稳定的东西当稳定的。
- **解决原则**：让测试的**采样口径与生产一致**；口径不一致的测试比没有测试更危险。
- **适用边界**：明确的单元测试不受此限；凡是「看起来像随机」的结论都要查口径。
- **验证实验**：同一被测对象，用两种采样各跑 20 次，看结论是否翻转。
- **案例**：稳定性测试拿 1 次采样去比 3 次投票，把不稳定误判成稳定。

### P-09 校验器要笨但死（反幻觉闸门） ｜类：不确定性 · 反馈

- **识别信号**：模型给出的结论引用了「原文」，但你没法确认那段原文真的存在。
- **底层机制**：生成模型会编引用；**让另一个模型去判断真假，等于用幻觉检查幻觉**。
- **常见误判**：「让模型自己再检查一遍」。
- **解决原则**：**用确定性代码逐字校验引用**（在源文件里做字符串匹配）；匹配不上就标记
  `UNVERIFIED` 并**降级**该结论，而不是照常输出。
- **适用边界**：只适用于能拿到原文的场景；拿不到原文时应标「无法核验」，不能默认成立。
- **验证实验**：故意塞一条伪造引用进流程，看它是否被标记。
- **案例**：每条结论的原文引用由代码逐字校验，找不到就标 UNVERIFIED 并降级。

### P-10 独立复核必须换厂家 ｜类：反馈 · 不确定性

- **识别信号**：用同一个模型/同一家服务的第二个上下文去「复核」第一份结论。
- **底层机制**：同一家的模型共享训练偏差，**会以同样的方式犯同样的错**；
  它只能查出「漏」，查不出「偏」。
- **常见误判**：「我换了新会话，等于独立复核」。
- **解决原则**：复核要**换厂家**（不同供应商的模型），同一目标、同一方法、**不许先看第一份结论**。
  不一致时，把**分歧点写成一句话**，针对它再查一轮。
- **适用边界**：查漏（有没有漏项）用同厂第二上下文就够；查偏（结论对不对）必须换厂家。
- **验证实验**：让两家各自独立跑同一目标，看是否出现**方向性分歧**。
- **案例**：跨厂复核被列为闭环的命门；同厂换上下文明确不算复核。

### P-11 失败要响，不要降级 ｜类：故障

- **识别信号**：主通道不可用时，代码/流程**悄悄**走了另一条路（直连、跳过校验、用缓存旧值）。
- **底层机制**：为了让流程「不中断」而写的兜底分支，把**安全失败**变成了**静默失效**。
- **常见误判**：「先让它跑起来」→ 真实身份/真实数据在无人察觉时暴露或写坏。
- **解决原则**：默认**失败即停止**（fail closed）；引导不行就掐断，掐断不行才报错交回用户。
  **绝不允许「引导失败就直连」这种降级。**
- **适用边界**：只读查询、非敏感任务可以降级，但必须**在输出里写明降级了**。
- **验证实验**：故意让主通道不可用，看系统是停下并报错，还是照常出结果。
- **案例**：出口守卫的设计原则 —— 优先引导换通道，引导不了就掐断，再不行才杀进程；不静默降级。

## 三、怎么长出新模式（这是本库的活水）

不要「编」模式，要**从真实事故里提炼**：

1. 发生一次事故 → 先照 `references/diagnosis-tree.md` 定位到根因。
2. 问一句：**「这个坑是只属于这个项目，还是会重复出现？」** 会重复 → 提炼成模式。
3. 用 `assets/pattern-card-template.md` 写卡，**必须**填「常见误判」和「验证实验」——
   没有验证实验的模式只是感想。
4. 找一条**反例**：什么情况下这个模式不成立？填进「适用边界」。**找不到反例的模式不许入库。**
5. 登记进本文件，并注明来源（哪次事故、哪份记录）。

**入库门槛**：有真实案例 + 有反例边界 + 有可做的验证实验。三条缺一不入。
