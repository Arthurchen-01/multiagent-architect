## v0.1.0.0 ｜2026-10-09 ｜首版

**做了什么**

- 新建技能包 `engineering-architect`（工程架构师），遵循 Agent Skills 开放标准。
- `SKILL.md`：开工四步闸门（出口 / 真相源 / 判档 / 一句能验收的话）+ 三档规模路由 +
  三条腿核实 + 换厂复核 + 交付四问 + 五种工作模式路由 + 六条反模式 + 加载地图。
- `references/pattern-library.md`：八类基础模式（分解/状态/约束/不确定性/反馈/资源/故障/演化）
  + **11 张模式卡**，每张都是**从本机项目真实事故里提炼**的，格式固定为
  「识别信号 → 底层机制 → 常见误判 → 解决原则 → 适用边界 → 验证实验 → 案例」。
- `references/diagnosis-tree.md`：五层诊断树（信息 → 理解 → 决策 → 执行 → 验证）
  + 区分性实验设计 + 六条常见弯路。
- `references/project-memory.md`：开工读什么、写什么（快照与账本分开 / 决策只追加 /
  教训带行动项）、并发写入规矩、交接卡与线卡的区别。
- `references/coach-mode.md`：七步训练闭环（先预测再反馈）、五类追踪指标、
  区分「识别错误」与「方案失败」、决策日志字段。
- `references/sources.md`：格式标准出处（agentskills.io 规范 / Anthropic 官方最佳实践）
  + 每条内容的来源 + **本 skill 明确不做的事** + 改这个 skill 的规矩。
- `assets/`：模式卡模板、决策记录模板、工程图七段汇报模板、触发评测集（14 条，含训练/验证划分）。
- `scripts/validate_skill.py`：只读校验器（规范合规 + 指纹扫描），退出码 0/1。

**为什么这么设计（依据）**

- **不拆成五个 skill**：初版拆多份会让每份的 description 都常驻，常驻成本变高；
  改用一个 skill + 按分支加载 reference。依据：Agent Skills 规范的渐进式披露。
- **references 用 ASCII 文件名**：换环境（不同客户端/编码）时更稳；中文标题写在文件内。
- **把用户的常驻规矩也写进来**：换到没有 `AGENTS.md` 的机器上时，这个 skill 要能独立工作。
  但 `sources.md` 里声明了**本机权威版本仍是 `AGENTS.md`**，两边冲突以它为准。
- **模式卡必须有「适用边界」和「验证实验」**：没有反例边界的模式只是感想；
  没有验证实验的模式没法证伪。入库门槛写在 `pattern-library.md` §三。
- **「宏大终局」写成待验证假设**：原讨论材料里它就是待检验的，不升级成结论。

**怎么验的**

- `python scripts/validate_skill.py engineering-architect` → **退出码 0**，`FAIL=0`。
- 校验项：`name` 合法且与目录同名 / `description` 530 字符（上限 1024）/
  `SKILL.md` 正文 89 行（上限 500）/ 引用的 9 个文件全部存在 /
  技能内文件全部能从 `SKILL.md` 一层直达 / 指纹扫描干净 / JSON 资源可解析。
- 指纹扫描：交付物里**没有** IP、Windows 绝对路径、MAC、凭据。

**已知没做**

- **没做真实触发测试**。触发率要跑 14 条查询 × 3 次 = 42 次调用，本版没跑。
  评测集已备好（`assets/trigger-eval.json`），第一次真实使用后补。
- **没有用真实任务跑过一遍**（原设计建议：拿两个差异大的项目试最小版）。
  所以本版是「按标准写对」，**不是「按实战验证过」**。
- 八类模式仍是**初始分类、非最终定论**（来源材料自己就是这么说的）。

**下一步（按优先级）**

1. 拿一个简单自动化活 + 一个多模块复杂活各跑一次，观察：判档对不对、状态有没有维护、
   验收是不是真能验收。
2. 跑一轮触发测试，按结果改 `description`（只用训练集改，验证集只用来检查过拟合）。
3. 每次被用户纠正，就往 `SKILL.md` §6 或 `pattern-library.md` 加一条 —— 这是最直接的迭代方式。

## v0.1.0.0 ｜2026-10-09 ｜发布前修订（同一版内，未开新版本号）

> 依据版本规矩「**发布前**的修订并进同一版」——这一版还没被真实任务用过，属于草稿，
> 不值得为改动开新文件夹。**被真实任务用过之后**再改，就要按四位升版本了。

**改了什么**

1. **装到三个环境，不只 dsh**。查清了三家各自的技能目录，并写成一条命令装全部：
   - dsh → `%USERPROFILE%\.dsh\skills\`
   - WorkBuddy → `%USERPROFILE%\.workbuddy\skills\`
   - Antigravity 2.0 / IDE → `%USERPROFILE%\.gemini\config\skills\`
   - Antigravity IDE 旧路径 → `%USERPROFILE%\.gemini\antigravity\skills\`
   - Antigravity CLI → `%USERPROFILE%\.gemini\antigravity-cli\skills\`
2. **发现并利用了一个本机事实**：dsh 与 WorkBuddy 的技能目录**是同一个文件夹的两个入口**
   （两个都是 junction，指向同一个共享技能库）。安装脚本会**自动去重**，只写一次、两边都可见。
3. **`install.ps1` 升级**：从「只装 dsh」变成「装全部 + 逐个规范校验 + 逐个哈希比对」，
   退出码 = 没通过的项数。加了 `-DryRun`。
4. **frontmatter 改成零多行结构**（兼容性保险）：`description` 与 `compatibility` 从折叠写法
   （`>`）改成单行字符串，`metadata` 改成单行流式写法。
   **为什么**：这个文件要被**三套不同的实现**解析，折叠标量是里面唯一的非平凡 YAML 结构，
   去掉它等于消掉一整类解析器风险，代价只是那几行不好看。

**怎么验的**

- `install.ps1` 跑通，**退出码 0**：5 个位置 → 去重后 4 个真实目标，全部
  `规范校验 OK=7 WARN=8 FAIL=0` + `11 个文件逐字节相同`。
- 逐个位置实测：5 个路径下的 `SKILL.md` 都是 **9456 字节 / 同一个 SHA-256 前缀**。
- **确认不需要注册**：Antigravity 的 `config.json` 里**没有任何技能注册字段**（0 命中），
  说明它就是扫目录 —— 所以放对文件夹就够了，不用改配置。
- **Antigravity 路径不是猜的**：来自官方文档《Agent skills》，并在本机
  `language_server.exe` 里核对到 `.agents/skills`（6 处）、`config/skills`（4 处）、
  `SKILL.md`（45 处）字符串。
- dsh 侧：装完后**本次会话的技能清单里已经出现** `engineering-architect`（自动触发已生效）。

**已知没做**

- **Antigravity 与 WorkBuddy 没有做「界面上真能看见」的验证** ——
  它们需要**重启/新会话**才会重新扫技能目录。文件位置与格式已按官方文档核对，但
  **「菜单里能不能看到」这一步要你重启后自己确认一次**。
